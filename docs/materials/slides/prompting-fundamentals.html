Part 1

How the model reads your prompt

LLM vocabulary, and what an AI assistant can and can’t see

LLM vocabulary

LLM

Large language model: predicts the next piece of text from patterns in its training data

Prompt

Everything you send the model: your question, pasted data, instructions

Token

The unit a model reads and writes; a word or part of a word

Context window

The maximum number of tokens the model can work with at once

System prompt

Hidden instructions the tool gives the model before your prompt

Hallucination

Confident output that is false: a made-up function, column or citation

Non-determinism

The same prompt can give different answers each time you run it

Agent

A model that can use tools (read files, run code) in a loop toward a goal

Non-determinism matters for the activity: pairs will get different outputs from the same prompt. That’s expected, and it’s another reason to verify.

Tokens: how the model reads text

Models don’t read words or characters. They read tokens.

Thesquirrelranuptheoaktree.

Illustrative split. The exact tokens depend on each model’s tokenizer.

Rules of thumb (English text)

  • One token is roughly ¾ of a word
  • Common words are one token; rare words, numbers and code split into several
  • Tools limit and bill usage in tokens

Why it matters for data work

  • A pasted CSV costs tokens for every value
  • glimpse() + 5 rows: a few hundred tokens
  • A full dataset can fill most of the window, leaving less room for your instructions

The context window

The model’s working memory for one request, measured in tokens. Everything below shares it:

System promptAttached filesChat historyYour promptResponse

What happens as it fills

  • The response has to fit too
  • Older messages may be summarized or dropped
  • Details buried in a long chat get less attention

What to do

  • Send structure, not raw data
  • One task per chat; start fresh when it drifts
  • Restate key constraints in the new chat

Note

Window sizes vary widely by model and tool, and change often. Check the docs for the one you use.

What’s in the context window?

The model answers using only what’s in its context window for this request.

Usually in context

  • Your prompt and the chat so far
  • Files or selections your IDE assistant attaches (open editor, @-mentioned files)
  • Output you paste in (errors, glimpse())

Usually not in context

  • The actual values in your data frame
  • Your project’s goals, field conventions, data-collection quirks
  • What you decided in a different chat

Tip

Long chats drift. When the model starts forgetting constraints, start a fresh chat with a short summary of what matters.

Show where your IDE (Positron Assistant, Copilot) shows which files are attached. What gets sent varies by tool and settings, so check yours.

What the model knows (and doesn’t)

It only knows what’s in context

  • It hasn’t seen your data unless you show it
  • Paste glimpse() output, column names, a few sample rows
  • Say what the data is: source, units, one row = ?

It predicts plausible text, not truth

  • Code that runs ≠ code that’s correct
  • It fills gaps with assumptions, silently
  • It tends to agree with your framing, even when it’s wrong

Four Tips

  1. Give context: data, goal, audience
  2. Be specific: tools, constraints, output format
  3. Iterate in small steps: one task per prompt, then review
  4. Verify: run it, check the data, ask for its assumptions

Core idea: the model’s output is only as good as the context it gets. Everything that follows is a way of supplying better context or checking the output.

The model tends to agree with you

Models are trained to be helpful, which can tip into sycophancy: following your framing even when it’s wrong (Sharma et al., 2023).

Leading prompt

“Why is fur color such a strong predictor of how squirrels react to people?”

Assumes the effect exists. You’ll likely get an explanation, not a check.

Neutral prompt

“Is there evidence in this data that fur color is related to how squirrels react to people? What would make that comparison unreliable?”

Asks for evidence and limitations.

Important

Ask questions that the data could answer “no” to.

Socratic Prompting

The neutral prompt above is an example of Socratic prompting. Instead of telling the model what to find, ask it what the evidence would need to look like.

Part 2

Prompting fundamentals

Context · specificity · iteration · verification

Anatomy of a good prompt

Context I’m working with the 2020 NYC Park Squirrel Census in R. One row = one squirrel sighting. Columns include fur color, location, height and free-text activities.

Task Write a cleaning script for the activities column.

Constraints Use tidyverse. Don’t drop or overwrite any original values; put derived columns next to the originals.

Output One R chunk, then a list of every value you couldn’t parse.

Check Before writing code, list your assumptions and ask me about anything ambiguous.

Note

Context doesn’t have to live in every prompt. Recall from our last workshop that a system prompt or project pre prompt can carry context so you don’t have to repeat it each time.

Five parts. Not every prompt needs all five, but the first one (context) and the last one (check) are the ones people skip.

Prompting fundamentals

Fundamental Weak prompt Stronger prompt
Context “Clean this data” “This is the 2020 NYC Park Squirrel Census, one row per squirrel sighting”
Role / audience (none) “I’m a data manager preparing this for a public archive”
Task + constraints “Make a plot” “Use ggplot2, colorblind-safe palette, one plot per park”
Output format Not specifying “Return a single R chunk plus 3 bullet caveats”
Surface assumptions (none) “Before writing code, list your assumptions about each column”
Invite pushback (none) “If my approach is flawed, say so before writing code”

The last two rows matter most

Models fill gaps silently. Asking for assumptions and pushback is how you catch data loss before it happens.

Show the model your data (safely)

The model can’t see your data frame. Give it the structure, not the whole dataset.

dplyr::glimpse(squirrels)          # column names, types, first values
head(squirrels, 5) |> knitr::kable() # a few example rows
dput(head(squirrels, 5))           # reproducible snippet it can run

Do

  • Paste schema + a few rows
  • Describe units and how the data was collected
  • Mention known messiness

Don’t

  • Paste sensitive or restricted data into tools your institution hasn’t approved
  • Assume the model knows your column meanings

Iterate in small steps

1 · Plan → 2 · Code one step → 3 · Run → 4 · Review → repeat

Instead of…

“Clean the data, fit a model and make five plots.”

Try…

“First, propose a plan in 4–6 steps. Don’t write code yet.”

Tip

Each step should be small enough that you can check it.

Verify before you trust

AI-written cleaning code can run perfectly and still lose data. Check it.

n_before <- nrow(squirrels)
clean    <- clean_squirrels(squirrels)   # AI-written function

stopifnot(nrow(clean) == n_before)       # no rows silently dropped

# how many new NAs did cleaning create in a column?
na_added <- function(before, after, col) {
  sum(is.na(after[[col]])) - sum(is.na(before[[col]]))
}

Prompts that help

  • “Which values does this code turn into NA?”
  • “Write tests that would fail if this code dropped data.”
  • “Explain this function line by line.”

Does being mean help?

Dobariya & Kumar (2025), Mind Your Tone

  • 50 multiple-choice questions (math, science, history)
  • Each rewritten in 5 tones → 250 prompts
  • Model: ChatGPT-4o
Tone Accuracy
Very polite ~80.8%
Very rude ~84.8%

Rude prompts scored ~4 points higher.

Before you start insulting Copilot…

  • One model, one version, 50 questions
  • Multiple choice ≠ writing your analysis code
  • Earlier work (Yin et al., 2024) found impolite prompts often hurt performance on older models
  • Open question: is it rudeness, or that rude prompts are shorter and more direct?

Note

Takeaway: Tone is a variable. Directness beats deference. Hostility isn’t the skill — clarity is.

Good discussion prompt: how would you design a study to separate “rude” from “concise”? This is a reproducibility lesson too: a single-model, single-run result is a hypothesis, not a rule.

Same data, three roles

2020 Park Squirrel Census (433 sightings, 24 parks) · “I am [role]. Clean this dataset for me.”

Different roles yielded different methods to to clean the data.

The four methods used were:

  • Preserved: script left the data intact without removing anything
  • Transformed: values were simplified or normalized, but original meaning kept
  • Interpreted: data changed shape (e.g. one column split into many), steering it toward a specific analysis
  • Discarded: values present in the raw data were silently dropped

Advance three times: data manager, then data science student, then environmental researcher. Same prompt, same data. The role decided what survived.

What the squirrels taught us

What happened

  • Same prompt, same data → three different datasets
  • Each role’s choices were reasonable for that role
  • The worst losses were silent: values became NA with no warning

How to prevent it

  • State your goal and what must be preserved
  • Ask for a list of every value that was changed or dropped
  • Compare row counts and NA counts before and after
  • Keep original columns; add derived ones beside them

Verify: the check function

In activity-starter.R, and worth keeping for any AI-written cleaning code:

check_cleaning <- function(before, after, col) {
  if (!col %in% names(after)) stop("Column '", col, "' was renamed or dropped")
  tibble::tibble(
    rows_before   = nrow(before),
    rows_after    = nrow(after),
    na_before     = sum(is.na(before[[col]])),
    na_after      = sum(is.na(after[[col]])),
    values_before = dplyr::n_distinct(before[[col]]),
    values_after  = dplyr::n_distinct(after[[col]])
  )
}

Tip

If na_after > na_before, the code turned real observations into missing data. Did the model warn you?

Part 4

From prompts to agents

Write it down once: agentic coding and skills

You just did the same work four times

In the activity, every round you:

  • pasted the same glimpse() output
  • retyped “keep the original column”
  • copied code from chat into R
  • ran the check yourself

Two questions

  1. What if the assistant could run the code and the check itself?
  2. What if you wrote your context and rules once, and it reused them every time?

That’s agentic coding (1) and skills (2).

Chat assistant vs. coding agent

Chat assistant

  1. You write a prompt
  2. It suggests code
  3. You copy, run and check it
  4. You paste back errors

You run the loop.

Coding agent (e.g. Claude Code)

  1. You describe the goal
  2. It reads your files and data
  3. It writes code, runs it, sees errors, fixes them
  4. You review and approve changes

It runs the loop. You stay the reviewer.

Tip

An agent can act on your files, so the fundamentals matter more, not less.

What is a skill?

A skill is a folder with a SKILL.md file: written instructions Claude follows for a specific kind of task.

  • Frontmatter: a name and a description of when to use it
  • Body: the steps and rules, in plain Markdown
  • Claude sees every skill’s description, and loads the full instructions only when a task matches
  • Or run one yourself: /safe-data-cleaning
  • Can bundle scripts, like our check function
my-project/
└── .claude/
    └── skills/
        └── safe-data-cleaning/
            ├── SKILL.md
            └── scripts/
                └── check_cleaning.R

Project skills live in .claude/skills/ and are shared through git. Personal ones go in ~/.claude/skills/.

1. Run `glimpse()` and `count()` on the target column.
2. List each kind of value and how you'll convert it.
3. Ask about anything ambiguous; wait for my answers.

## Rules
- Never overwrite or drop original columns; add new ones.
- Never drop rows. Use the tidyverse.

Key takeaways

1 Context is everything. The model only knows what you show it.

2 Be specific. Tools, constraints, output format.

3 Go step by step. Plan first, then one task at a time.

4 Ask neutral questions. Let the data say “no.”

5 Surface assumptions. Ask what it changed or dropped.

6 Verify. Row counts, NA counts, tests. You’re the scientist.
